\section{Hardware Setup and Input Data Preparation}

This section describes the hardware setup used for data collection and the preparation of input data for the proposed risk-annotated scene graph pipeline. In a complete deployment scenario, the system is expected to operate on a mobile robot equipped with an RGB-D camera and sufficient onboard computing resources to run the full perception, mapping, and risk-assessment pipeline in real time. Such a setup would allow sensor data acquisition, semantic interpretation, scene graph construction, and risk annotation to be performed directly on the robot.

For the current development and evaluation phase, however, the available hardware is distributed across three separate components: the RGB-D sensing unit, the mobile robotic platform, and the external processing unit. The RGB-D sensor used in this work is an Intel RealSense D455 camera, which provides synchronized color and depth information. The mobile platform is a Unitree Go1 quadruped robot, which provides the physical mobility required for collecting data in indoor environments. The processing unit is an NVIDIA Jetson Thor, which is intended to execute the computationally demanding components of the pipeline, such as visual-language-model-based reasoning and semantic scene graph processing.

In the present setup, the Unitree Go1 does not provide the required hardware interface to power and operate the NVIDIA Jetson Thor directly as an onboard edge-computing device. Therefore, the system is used primarily for data collection, while the computationally demanding components of the pipeline are executed later on the NVIDIA Jetson Thor. The Intel RealSense D455 is rigidly mounted on the Unitree Go1 using a 3D-printed frame and connected to the robot's onboard computer through USB. During operation, the RGB-D sensor data, camera calibration information, and robot odometry are transmitted to a local computer through Ethernet and recorded as a ROS bag. If required, additional camera sensor information, such as IMU measurements from the RealSense device, can also be included in the recorded dataset for future pose-estimation or sensor-fusion extensions. The recorded data can then be replayed at real-time speed for offline processing, testing, and debugging. This workflow is useful during development because the perception and risk-assessment pipeline can be evaluated repeatedly without physically operating the robot for every debugging cycle.

Although wireless transmission of the sensor data is technically possible, it was not selected as the primary data-transfer method because RGB-D streams require high and stable bandwidth. In particular, transmitting raw color images, aligned depth images, and odometry data over Wi-Fi can lead to frame drops, variable latency, and reduced synchronization reliability. Since accurate temporal alignment between RGB-D frames and robot odometry is important for later preprocessing and 3D scene reconstruction, Ethernet is preferred for data collection. This provides a more stable connection between the robot and the local recording computer and reduces the risk of incomplete or inconsistent ROS bag recordings.

From a software perspective, the hardware setup also requires an interface between two ROS versions. The Unitree Go1 currently operates using a ROS 1-based software stack, while the proposed risk-annotated scene graph pipeline is developed in ROS 2. Therefore, during data collection, both the RealSense D455 driver and the Unitree Go1 odometry interface are operated within the ROS 1 environment on the robot side. The RGB-D data, camera calibration information, and robot odometry are transmitted to the local computer and stored as a ROS 1 bag. For offline processing, this recorded data is converted into a ROS 2-compatible bag format before being replayed through the proposed ROS 2 pipeline. This also implies that, for an actual deployment of the complete system, the parent robotic platform should either provide a native ROS 2 software interface or use a dedicated ROS 1-to-ROS 2 bridge to transfer the required sensor and odometry data into the ROS 2 processing pipeline in real time.



\subsection{Data Preprocessing}

After the recorded dataset has been converted into a ROS 2-compatible format, the sensor streams are replayed as timestamped inputs to the proposed pipeline. These streams cannot be passed directly to the risk-annotated scene graph pipeline, since the downstream modules require each input sample to contain a consistent combination of visual data, depth data, camera calibration, and pose information. The purpose of the input pre-processing stage is therefore to transform the raw replayed streams into a structured RGB-D-pose frame for the main perception and scene graph processing modules.

The first task of the pre-processing stage is temporal association. The RGB image, aligned depth image, and camera calibration message are synchronized according to their timestamps. The RGB image provides the visual observation used for segmentation and semantic interpretation, while the depth image provides the geometric information required to estimate the 3D position of image regions. If RGB and depth data correspond to different time instants, object masks or bounding regions extracted from the RGB image may be projected using incorrect depth values. Therefore, only RGB, depth, and calibration data that can be associated within a defined synchronization interval are considered for further processing. Each RGB-D observation is also associated with a pose estimate. The robot odometry provides the pose of the robot base, while the camera is assumed to be rigidly mounted on the robot. Under this assumption, the camera pose is derived by combining the robot odometry with the fixed transform between the robot body and the camera. If odometry is not available exactly at the image timestamp, the pose can be obtained using the nearest valid odometry sample or by interpolating between neighbouring odometry samples.

The second task is format normalization. The baseline framework processes each sample using an RGB image, a depth image, a translation vector, and a rotation matrix. Therefore, the ROS-based pre-processing stage prepares the incoming camera streams so that they can be converted into the same logical representation. The color image is represented as an 8-bit RGB image, which provides a consistent image format for the segmentation and visual reasoning stages. If the input image is already available in this format, additional conversion can be skipped. Depth data also requires normalization. Depending on the sensor or dataset, depth images may be represented as unsigned 16-bit integer values or as 32-bit floating-point values. In many RGB-D camera streams, 16-bit depth values represent distance in millimetres. For geometric reasoning, the scene graph pipeline requires metric depth values. Therefore, the depth image is converted into a 32-bit floating-point representation in metres. If the input depth image is already represented as metric floating-point depth, no unit conversion is required.

The pre-processing stage also checks the spatial consistency and validity of the depth data. Since object regions are detected in the RGB image and then combined with corresponding depth values, the depth image must be aligned with the RGB image. A resolution mismatch between RGB and depth data indicates that this correspondence may not hold directly, and such frames can therefore be rejected. In addition, depth cameras may produce invalid or unreliable measurements due to reflective surfaces, transparent objects, occlusions, motion, or sensor range limitations. The pre-processing stage identifies depth values that are not finite or lie outside the expected measurement range. From this, an invalid-depth ratio can be computed for each frame. If the invalid portion of the depth image is too high, the frame may not contain enough reliable geometric information for object localization and scene graph construction. For real-time operation, this check can also be performed on sampled pixels to reduce processing cost.

Optional camera IMU data can also be preserved. The IMU stream may contain angular velocity and linear acceleration measurements that can support future extensions such as visual-inertial odometry, motion analysis, or sensor fusion. In the current system, the IMU is not used to modify the camera pose. Since the camera is assumed to be fixed relative to the robot body, the camera orientation is derived from robot odometry and the fixed base-to-camera transform. The IMU data is therefore treated as optional supplementary information.

Frames that fail the required consistency checks are not forwarded to the main processing stage. A frame may be rejected if the image dimensions are incompatible, if the depth encoding cannot be interpreted, if the invalid-depth ratio is too high, or if no suitable odometry estimate is available. The pre-processing stage also includes a latency guard. If the processing time of a frame exceeds a configured threshold, processing is stopped at the next safe checkpoint and the frame is dropped before publication. This prevents significantly delayed frames from entering the downstream pipeline and disturbing real-time processing.

The output of the input pre-processing stage is a prepared RGB-D-pose frame. This frame contains the synchronized RGB image, metric depth image, camera calibration, camera pose, timestamp, frame identifier, synchronization information, and optional IMU data. The calibration contains the intrinsic parameters required to relate image coordinates to 3D rays, allowing image-space detections to be projected into 3D using the depth image. This prepared representation can then be converted into the baseline framework structure containing the image data, depth data, translation vector, and rotation matrix.
